韓国の AI コンテスト・ハッカソン情報を毎日自動で集めるサービスで、キーワードルールが判断に迷う掲載を Jev にもう一度問い合わせる仕組みを作りました。テキストではなく確率付きの決まった形式の答えを返すモデルが、実運用でどう使えるかを記録します。

왜 Jev를 썼나

なぜ Jev を使ったか

국내 AI 대회 정보는 공모전 플랫폼, 정부·지자체 공고, 기업 보도자료에 흩어져 있습니다. 11개 사이트에서 하루 약 4,000건의 공고를 모아 "AI 대회가 맞는지, 어떤 분야인지"를 가려야 했습니다.

처음에는 LLM으로 검색했지만, 매일 돌리기에는 토큰 비용이 비효율적이었습니다. 그래서 수집과 판정을 정해진 키워드 규칙으로 바꿨습니다. 그런데 규칙에는 두 가지 한계가 있었습니다.

  • 제목에 데이터나 SW만 들어가도 AI 대회로 잡힙니다.
  • 반대로 "AI"라는 단어 없이 AI를 다루는 대회는 놓칩니다.

대화형 LLM에 물으면 답을 문장에서 다시 파싱하고 검증해야 합니다. Jev는 질문의 형식(예/아니오, 선택지)에 맞춰 확률값을 바로 돌려줍니다. 그래서 답을 그대로 if 문에 넣을 수 있었고, 이 점이 이 문제에 맞다고 판단했습니다.

韓国の AI 大会情報は、コンテスト掲載サイト、行政・自治体の公告、企業のプレスリリースに分散しています。11 のサイトから 1 日約 4,000 件の掲載を集め、「AI 大会かどうか、どの分野か」を判定する必要がありました。

当初は LLM で検索していましたが、毎日回すにはトークン費用が非効率でした。そこで収集と判定を決まったキーワードルールに切り替えました。しかしルールには二つの限界がありました。

  • タイトルに データ や SW が入っているだけで AI 大会と判定されてしまう。
  • 逆に「AI」という語がなくても AI を扱う大会を取りこぼす。

対話型 LLM に聞くと、答えを文章から改めてパースし検証する必要があります。Jev は質問の形式（はい/いいえ、選択肢）に合わせて確率値をそのまま返します。そのため答えをそのまま if 文に使えることが、この問題に合っていると判断しました。

Jev는 한국어보다 영어를 더 잘 읽습니다. 그래서 규칙을 기본으로 두고, Jev가 확신할 때만 규칙을 뒤집도록 임계값을 보수적으로 잡았습니다.

Jev は韓国語より英語の方が得意です。そのためルールを基本とし、Jev が確信しているときだけルールを覆すよう、しきい値を保守的に設定しました。

한 번 물어본 공고는 제목과 설명의 해시로 캐시합니다. 그래서 매일 실행할 때는 새로 올라온 공고만 Jev에게 보냅니다. 실행마다 판정 결과, 지연 시간, 토큰, 비용을 jev_runs.jsonl에 남기고 관리자 페이지에서 확인합니다.

一度問い合わせた掲載はタイトルと説明のハッシュでキャッシュします。そのため毎日の実行では新しく掲載されたものだけを Jev に送ります。実行ごとに判定結果、レイテンシ、トークン、費用を jev_runs.jsonl に記録し、管理画面で確認できます。

써보며 알게 된 점

使ってみて分かったこと

답을 파싱할 필요가 없다

확률과 선택지로 답이 오기 때문에 JSON 파싱 실패나 형식 검증 코드가 필요 없었습니다. 판정 로직이 임계값 비교 몇 줄로 끝납니다.

回答をパースする必要がない

確率と選択肢で答えが返るため、JSON のパース失敗や形式検証のコードが不要でした。判定ロジックはしきい値の比較数行で済みます。

규칙을 대체하기보다 보완할 때 강하다

대부분(95%)은 규칙과 같은 판단이었고, 차이는 규칙이 약한 가장자리에서 났습니다. 그래서 "규칙 우선, Jev는 확신할 때만"이라는 구조가 비용과 안정성 모두에 맞았습니다.

ルールを置き換えるより補完するときに強い

大半（95%）はルールと同じ判断で、差はルールが弱い境界部分で出ました。そのため「ルール優先、Jev は確信があるときのみ」という構成が、費用と安定性の両面で合っていました。

캐시와 함께 쓰면 운영비가 사실상 0에 가깝다

출력 토큰이 무료이고 입력도 짧아, 캐시를 붙이면 매일 새 공고만 판정하는 비용이 1센트에도 못 미칩니다. 서버·DB 없이 GitHub Actions만으로 운영합니다.

キャッシュと併用すると運用費はほぼゼロ

出力トークンが無料で入力も短いため、キャッシュを付ければ毎日新しい掲載だけを判定する費用は 1 セントにも満ちません。サーバー・DB なしで GitHub Actions だけで運用しています。

한국어 입력에는 보수적인 임계값이 필요하다

영어에 비해 한국어 판단에는 확신이 덜할 수 있다고 보고, 규칙을 뒤집는 조건을 좁게 잡았습니다. 이 임계값이 적절한지는 아래 평가로 검증합니다.

韓国語の入力には保守的なしきい値が必要

英語に比べ韓国語の判断は確信度が下がり得ると考え、ルールを覆す条件を狭く設定しました。このしきい値が適切かは、下の評価で検証します。
